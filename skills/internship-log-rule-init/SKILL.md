# 实习日志规则初始化

单文件执行手册。**只产出规则文件第一版；不写日志、不审日志、不月结。**

## 与 rule-maintain 的分工

- **rule-init（本 skill）**：没有规则，或要整体重写规则。
- **rule-maintain**：已有规则，只做小步增删改，并同步执行 skill。

如果用户已经有规则、只想改几条，停在这里，改用 `internship-log-rule-maintain`。

## 先分清三种东西

访谈和落盘时，每条要求先归位：

- **内容标准**：记什么、怎么记、保密范围、月结和素材库的字段 → 规则文件
- **流程**：怎么问、怎么落盘、怎么交付、怎么检查 → 留给执行 skill，不写进规则
- **实现细节**：目录名、文件名、链接写法、具体工具 → 留给执行 skill，不写进规则

用户说不清时，问一句「这条是标准还是做法」，不要替用户决定。

## 第一步：确认输出位置与前提

1. 问用户把规则文件写到哪里。**不要用默认路径，不要写进插件目录。** 规则实例属于用户数据，插件内只有 `templates/规则.template.md` 模板。
2. 问用户是否已经有规则文件。已有且只需小改，转 `internship-log-rule-maintain`；已有但要整体重写，先让用户确认旧文件怎么处理（备份、覆盖或另存）。
3. 读插件根下 `templates/规则.template.md`（相对本 skill 为 `../../templates/规则.template.md`），以它的章节顺序为骨架；模板只是骨架，不承载用户的具体标准。

## 第二步：访谈

一次只问一个问题，等用户回答再问下一个。按下面顺序把规则需要的内容问清楚；用户已经明确说过的，不要重复问。

1. **为什么写**：实习结束时要拿出什么？判断一篇日志有没有用的标准是什么？
2. **三层结构**：原料、月结、成品分别是什么？每层放在哪里、由谁产生？
3. **目录约定**：用户数据目录怎么组织？公司、岗位、月份、主题笔记、架构图分别怎么命名？哪些结构是必须遵守的约定，哪些只是执行 skill 的实现细节？
4. **每天写什么**：每天必写哪几块？每块的最低要求是什么？没内容时写「无」还是省略？
5. **待问怎么收口**：待问怎么分类、怎么标归属？每周和月底怎么清理？什么情况下直接删除？
6. **业务理解怎么记**：什么时候写？写哪几项？版本号怎么递增？未验证的判断怎么标？
7. **代码和架构图怎么记**：代码不存原文时，改成什么写法？架构图画到什么范围？放在哪里？
8. **和 AI 协作的约定**：提问节奏、答不上来怎么记、写完怎么确认、是否自动提交、哪些话不能说？
9. **保密**：仓库名/系统名能不能写？哪些凭证、客户信息、内网信息、代码原文不能写？公开发布前怎么检查？
10. **月结与素材库**：本月小结写几项、每项写什么？素材库有哪些字段？一个月挑几条案例？案例不够格时怎么办？
11. **待完善**：哪些事暂定不做，或以后再补？

## 第三步：写规则文件

- 按模板章节顺序写，不跳节、不合并节；用户明确不需要的节可以保留标题并写「暂不适用」，不要悄悄删掉。
- 每条标准写清适用条件和反面例子，不写「要写得更好」这类空话。
- 只写内容标准；如果用户给出的只是执行细节（如主题笔记目录名、`[[链接]]` 写法、具体工具），记到「待同步给执行 skill」清单，不写进规则；用户明确要求写进规则的目录约定，按用户要求保留。
- 开头写明「这份文件是唯一规则源」。
- 不把用户没说的标准补进去；用户答不上来的，写「待定」并放进「待完善」，不要替用户编。
- 不写日志正文、不写素材库、不写月结。

## 第四步：交付前检查

- 规则文件已写到用户指定路径，没有写进插件目录
- 章节顺序与模板一致；每节都有内容或明确的「暂不适用 / 待定」
- 标准、流程、实现细节已经分开；规则里没有混进用户不想写进去的实现细节
- 没有编造用户没说的标准、数字、结果
- 同一件事只有一套说法；新增条款和已有条款不冲突
- 需要同步到执行 skill 的实现细节已列成清单，交给用户决定是否走 `internship-log-rule-maintain`
- 本 skill 不写日志、不审日志、不月结、不 `git commit`

## 禁止

- 不替用户决定「规则要多严」
- 不把临时的一次性做法写成规则
- 不为了齐整扩写规则，不写散文
- 不把插件模板当成用户规则来改
- 不在插件目录里生成规则实例
- 不 `git commit`
