# 实习日志规则维护

单文件执行手册。**只管规则文件本身——写什么、放哪、改了之后谁来跟。不执行写日志、审核、月结。**

## 先分清三种东西

任何改动先归位，别混：

- **内容标准**：记什么、怎么记、保密范围、月结和素材库的字段 → 规则文件
- **流程**：怎么问、怎么落盘、怎么交付、怎么检查 → 四个执行 skill
- **实现细节**：目录名、文件名、链接写法、具体工具 → 执行 skill，不进规则

判断不了就问用户一句「这条是标准还是做法」，不要自己塞。

## 第一步：确认输入与目标

1. 问清用户要改什么：新增 / 修改 / 删除，具体到一句话。
2. 按插件根目录的 `references/workspace.md`（`${CLAUDE_PLUGIN_ROOT}/references/workspace.md`）读项目根目录的 `.claude/internflow.local.md` 定位规则文件；有配置且用户给了新路径时按 workspace.md 直接更新；没有配置时只询问规则文件路径，不强行创建配置，`log_root` 留到写日志或月结时补全；路径失效时询问用户，不要猜。
3. 确认规则实例路径。规则实例只在用户数据目录，插件内只有 `templates/规则.template.md`（`${CLAUDE_PLUGIN_ROOT}/templates/规则.template.md`）；不要把插件模板当成用户规则来改。
4. 读规则文件全文，读四个执行 skill（`internship-log`、`internship-log-review`、`internship-log-monthly`、`internship-log-retro`）和插件根目录 `README.md`（`${CLAUDE_PLUGIN_ROOT}/README.md`）的「规则章节顺序」表，找出哪些地方已经引用了这条内容——引用处、复述处和节号副本都是后续的同步点。
5. 确认改动属于上面哪一类；跨类时拆开处理（标准进规则，流程进 skill）。

## 第二步：改规则文件

- 只改用户要改的那节，不动相邻内容；保持章节顺序和术语与全文一致。
- 新增标准时写清适用条件和反面例子，不写「要写得更好」这类空话。
- 不把实现细节（目录名、文件名、某个工具）写进规则——这类留在执行 skill。
- 规则文件开头已声明「唯一规则源」，改完要保证全文仍成立：同一件事不出现两套说法。
- 如果新增、删除或重排了章节，先确定新的节号，再进入第三步；节号变化会影响四个执行 skill 里的「按规则第 X 节」引用。

## 第三步：同步执行 skill

规则改了，四个执行 skill 里凡是引用或复述了这条的地方都要跟着动，否则规则和执行会对不上：

- 先列出受影响的文件和原句，展示给用户确认，再开始改
- 逐个改：能引用规则的改写成「按规则第 X 节」，必须内嵌的保持与规则一字不差
- 章节增删或重排时，全局搜索 `按规则第`，按新节号逐个更新；同时更新「第 X 节『节名』」里的节名
- 没受影响的，明确说「无影响」
- 若某条标准在四个 skill 里被反复抄，建议改成「按规则第 X 节」，减少今后同步；但由用户决定是否动
- 插件根目录的 `README.md`（`${CLAUDE_PLUGIN_ROOT}/README.md`）的「规则章节顺序」表和其中的「按规则第 X 节」也要跟着改；这张表和 skill 里的引用一样是节号的副本
- 检查 skill 和 README 有没有复述规则里的数字（如提问轮数、明天条数、未解决条数）；有就改成「按规则第 X 节」，或明确标注为本 skill 的操作阈值
- 改完运行 `node ${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs`，确认节号范围、章节名和 README 表格一致；脚本在插件目录内，用户项目根没有，不要用相对路径

## 第四步：交付前检查

- 改动已归到正确文件：标准在规则、流程在 skill、细节不在规则
- 规则文件和四个 skill 之间，同一件事只有一套说法
- 规则里没有混进实现细节
- 新增条款和已有条款不冲突；冲突的说明以哪个为准
- 所有「按规则第 X 节」引用都指向正确的节；章节重排后已全部更新
- 插件根目录 `README.md`（`${CLAUDE_PLUGIN_ROOT}/README.md`）的章节表、节号引用和数字复述已同步
- `node ${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs` 通过
- 这个 skill 不改日志正文、不出日志内容、不 `git commit`

## 禁止

- 不替用户决定「规则要多严」，只落用户认可的标准
- 不把临时的一次性做法写成规则
- 不为了齐整扩写规则，不写散文
- 不跳过同步检查；改了规则不核 skill 就说「无影响」也算漏
- 不修改插件内的 `templates/规则.template.md` 来替代用户规则
